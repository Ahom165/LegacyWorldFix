PROOF — Player data repair (LegacyWorldFix 1.8.1, Minecraft 26.3)
==================================================================

SYMPTOM REPORTED
----------------
World converts and loads fine, but the player's inventory / position / XP
("l'inv et les cos du joueur") do not carry over: the game spawns a fresh
player.

ROOT CAUSE — found in the decompiled 26.3 game sources
------------------------------------------------------
1) net.minecraft.world.level.storage.LevelResource (26.3):

     public static final LevelResource PLAYER_DATA_DIR = new LevelResource("players/data");
     public static final LevelResource PLAYER_OLD_DATA_DIR = new LevelResource("players");

   net.minecraft.world.level.storage.PlayerDataStorage (26.3) reads ONLY
   <uuid>.dat / <uuid>.dat_old from that folder - the historical name-based
   fallback (players/<name>.dat) is GONE in 26.x:

     public Optional<CompoundTag> load(final NameAndId nameAndId) {
        Optional<CompoundTag> optTag = this.load(nameAndId, ".dat");
        if (optTag.isEmpty()) this.backup(nameAndId, ".dat");
        return optTag.or(() -> this.load(nameAndId, ".dat_old")).map(tag -> {
           int version = NbtUtils.getDataVersion(tag);
           return DataFixTypes.PLAYER.updateToCurrentVersion(this.fixerUpper, tag, version);
        });
     }

2) net.minecraft.server.players.PlayerList (26.3) - how the singleplayer
   owner's file is resolved:

     public Optional<CompoundTag> loadPlayerData(final NameAndId nameAndId) {
        UUID lastSingleplayerOwnerUUID = this.server.getWorldData().getSinglePlayerUUID();
        if (this.server.isSingleplayerOwner(nameAndId) && lastSingleplayerOwnerUUID != null) {
           return this.playerIo.load(new NameAndId(lastSingleplayerOwnerUUID, "<singleplayer owner>"));
        } else {
           return this.playerIo.load(nameAndId);
        }
     }

   ... and PrimaryLevelData.parse reads that key from level.dat:
   input.get("singleplayer_uuid").flatMap(UUIDUtil.CODEC::parse).

3) Mod <= 1.8.0 extracted the level.dat player correctly (PLAYER datafixer
   chain, nil-uuid fallback, singleplayer_uuid recorded) but wrote the file
   to <world>/playerdata/ whenever the per-dimension chunk layout was
   detected (StorageLayout coupled the two layouts). This 26.3 build reads
   chunks from dimensions/minecraft/<dimension>/ (DimensionStorageFileFix is
   shipped) AND players from players/data/ - the two folders moved in
   different releases and are NOT coupled. The player file therefore landed
   in a folder the running game never opens => fresh player at every launch.

   net.minecraft.util.filefix.fixes.PlayerStorageFileFix (the vanilla move,
   filefixer schema 4772) confirms the direction:

     addFileFixOperation(move("advancements", "players/advancements"));
     addFileFixOperation(move("playerdata",     "players/data"));
     addFileFixOperation(move("stats",          "players/stats"));

FIX (1.8.1)
-----------
- StorageLayout.playerDataDir() now resolves LevelResource.PLAYER_DATA_DIR
  of the RUNNING build (players/data on 26.3) instead of guessing from the
  chunk layout.
- StorageLayout migration direction corrected to the vanilla
  PlayerStorageFileFix direction (playerdata -> players/data, advancements
  -> players/advancements, stats -> players/stats), with per-file merge when
  the target already exists (game-written files win).
- New PlayerDataUpgrader: vanilla-order extraction of the level.dat player
  (BEFORE the LEVEL chain, like LevelDatToSavedDataFileFix), migration of
  legacy players/<name>.dat files under the deterministic OfflinePlayer:<name>
  uuid, singleplayer_uuid backfill when the owner file is unambiguous,
  repair of worlds converted by mod <= 1.8.0.
- needsLayoutMigration now also reports these player-repair cases (Player
  tag still in a stamped level.dat, name files without migrated counterpart)
  so the launch flow runs the repair; the check is convergent (false once
  repaired), so no repeated conversion screens.

---------------------------------------
